# Group 4 NFV monitoring simulation

This package reconstructs the traffic monitoring, bandwidth threshold, controller feedback and standby-router behaviour of Yang et al., FGCS 93 (2019), DOI 10.1016/j.future.2018.08.050. It implements a fluid discrete-event model in Python. It does not run OpenStack, OVS, AMQP, MongoDB, VRRP packets, or an actual network. Python dictionaries/lists represent collected records and the controller state. All reported system results are generated by the included code, not copied from the paper.

## Run on Windows

Install Python 3.10 or newer. Open a terminal in this extracted folder.

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run_all.py
```

For another operating system, use `python3 -m venv .venv`, install requirements with `.venv/bin/python`, then run `.venv/bin/python run_all.py`.

The script runs verification tests before experiments. Expected: `Ran 15 tests ... OK`. It creates 1,110 system runs (360 main, 360 telemetry-loss, 120 HA, 270 capacity). Some settings repeat across experiment families deliberately. It also runs the supplementary threshold sensitivity study (seed 42 and seeds 0–19). Run `python -m unittest discover -s . -p test_model.py` for tests alone.

## Files and outputs

- `nfv_model.py`: event queue, trace generator, counters, control, failover and metrics.
- `run_experiments.py`: repeated system experiments and four system figures.
- `test_model.py`: analytic and behavioural verification.
- `threshold_study.py`: supporting experiment adapted from the supplied threshold script.
- `results/summary.json`: settings, means, sample SD, valid sample counts, runtime and model SHA256.
- `results/*_runs.csv`: all per-run raw results.
- `results/example_trace.json`: seed-7 poll records, control actions, incident times and router events.
- `results/*.png`: plots used in the report.
- `results/thresholds/`: supplementary threshold outputs.

## Model assumptions

Four sources offer piecewise-constant rates that change each simulated second. Offered Mbps are integrated exactly between events into bytes using `125000 bytes per Mbps-second`. The active node counts ingress before policy and capacity drops; during an outage no traffic reaches its counters. A rate above K triggers a telemetry/controller pipeline and a 60-second source block. Counters continue observing attempted ingress during blocks. Rules retain their expiry across failover as a simplifying assumption. Capacity overload drops traffic proportionally without a queue. This is a fluid approximation and does not model TCP congestion control or per-packet delay.

The system background has lognormal location ln(5.5), scale 0.25, and independent 2% Pareto bursts capped at 35 Mbps. This is distinct from the supplied calibration generator (scale 0.45, 3% capped Pareto tail). Calibration and system randomness use separate streams. A 35 Mbps legitimate backup runs for seconds 420–440. Three deliberately labelled source-rate incidents last 20, 60 and 3 seconds at 25, 60 and 80 Mbps. Each start shifts independently by an integer 0–59 seconds per seed to vary alignment with polls. Synthetic incident labels define experiments and do not prove a real user is malicious.

Main runs use seeds 0–29, capacity 100 Mbps, polling 1/10/30/60 seconds, telemetry delay Uniform(0.05,0.25) seconds, processing 0.02 seconds, installation 0.10 seconds, and no message loss. Sensitivity runs use message-loss probability 0/0.1/0.3. Delays are assumed inputs. Message loss has no retry; received messages after the 600-second horizon are not processed. Poll counts represent telemetry batches of four sources, not packet or database overhead.

Master failure occurs at 350 + Uniform(0,1) seconds. A historical RFC 5798-inspired timer has master-down interval `(3+(256-priority)/256)*advert`, priority 150, and 2 seconds additional startup. HA experiments vary advertisement interval 0.5/1/2 seconds and use uniform failure phase over each interval. The model measures outage from the failure to activation, allowing for the last advertisement. The 2-second startup is assumed. This is not a full protocol implementation or calibration to the paper's 3–13-second results. Counter epochs reset at activation. Interval rates after activation use elapsed time since that reset; stale messages/commands from prior epochs are ignored.

## Metrics and interpretation

Window FPR is the proportion of delivered source-window measurements containing no incident overlap that exceed K. It differs from benign policy drop, which counts legitimate bytes denied by installed rules, including after an incident ends. Incident detection counts a flag delivered while a corresponding incident is still active; later alerts do not rescue that metric. Large-event delays are conditional on detected runs (`n` appears in summary.json). A new-block time is not necessarily the first protection time: the source might already be blocked by an earlier false alarm. The report emphasizes detection delay and actual forwarded/dropped bytes.

Interval counter RMSE compares counter-derived rates against the same time window of original offered rates. Near-zero error is an accounting check under exact counters. Current-rate RMSE compares a delivered interval average with the instantaneous offered rate at arrival. It measures smoothing/staleness, not sensor accuracy. Outage and throughput results depend on chosen timers, offered demand and capacity. Do not present them as observed hardware performance, confirmed malware detection, or the paper's deployment measurements.
